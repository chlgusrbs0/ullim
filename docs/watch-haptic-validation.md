## 같은 강도·총 길이의 비교 도구

감지를 중지하고 **설정 → 진동 진단 → 연속 출력 비교**를 연다. A–D 모두 `AndroidWaveformDevice`, `USAGE_TOUCH`, amplitude220, 총 요청600ms를 사용한다. 기존 긴 진단과 달리 live 파형 어댑터와 속성도 맞춘다. 마이크/DSP/AI는 이 합성 출력 비교에 참여하지 않는다.

| 버튼 | 한 OS 호출의 구성 | 호출 횟수 | 분리할 요인 |
|---|---|---:|---|
| A | 600ms 한 구간 | 1 | 같은 속성의 단일 긴 진동 기준 |
| B | 20ms 같은 강도30구간 | 1 | 동일 파형 내 구간 분할 |
| C | 60ms 한 구간 | 10 | 현재 live 청크와 같은 반복 교체 주기 |
| D | 200ms 한 구간 | 3 | 교체 주기 차이. live 기본값은 변경하지 않음 |

각 버튼을 충분히 구분할 간격을 두고 반복한다. 손목 착용/접촉 상태와 시스템 진동 설정을 유지한다. 비교 순서가 알려진 진단이므로 #37 블라인드 구별 시험의 성적으로 사용하지 않는다. A/B는 매끈하고 C가 끊기면 반복 교체가 주원인이라는 근거가 강화된다. B도 끊기면 구간 처리/OS 어댑터도 조사한다. A까지 끊기면 USAGE_TOUCH 속성·기기 설정과 기존 진단의 차이도 조사한다. 어느 결과도 관찰 전에 가정하지 않는다.

완료 화면의 명령 수와 `UllimHaptics` 로그를 함께 확인한다. 로그는 합성 패턴, 상태, 명령 수, 앱 일정 최대 지연(ms)뿐이며 분류명/원음/예외 메시지는 포함하지 않는다. 이 값은 main Handler의 예정 호출 시각과 실제 호출 시각 차이이며, 소리→모터 지연이나 모터가 실제 진동한 시간은 아니다. 일정이40ms 넘게 늦으면 남은 일정을 취소한다. LATE/FAILED/STOPPED 실행은 정상 완료 비교로 쓰지 않는다. 화면을 나가거나 다른 진단을 누르면 대기 콜백과 출력을 취소하며, 무한 반복하지 않는다.

실기기 A/B/C/D를 사용자가 직접 반복 실행했다. 결과는 **A 매끈 / B 매끈 / C 끊김 / D는3번 울림을 구별하며 C보다 끊김이 덜함**이었다. 분할된20ms구간 자체보다 반복 OS 호출이 주요 원인이라는 근거다.200ms로 늘리는 것만으로 매끈한 연속 출력이 된 것은 아니다. live 기본값을 단순히200ms로 바꿔 해결했다고 처리하지 않는다.

[명령 완료 요약](evidence/issue18-comparison-command-summary.txt)에는 SINGLE/SEGMENTS 각1회, CHUNKS_60 각10회, CHUNKS_200 각3회로 완료한 반복 실행이 남아 있다. 관찰된 앱 일정 최대 지연은0–26ms로40ms중단 기준 이내였다. 이 값은 물리 지연이 아니다. [동일 앱 시스템 파형 기록](evidence/issue18-os-waveform-records.txt)에는600ms 내의20ms 구간과60/200ms 호출 기록을 남겼으며 원본 PCM·분류명·연결정보는 포함하지 않는다. 시스템 덤프 역시 실제 모터 가속도 계측은 아니다.

추가 비행동 검사에서 오디오 서버 덤프가 `SEC_AUDIO_SUPPORT_HAPTIC_OUTPUT = FALSE`라고 보고했다. 이어서 SDK36으로 컴파일한 임시 진단 클래스를 같은 워치의 `app_process`에서 실행해 공개 API를 직접 조회했다. `AudioManager.isHapticPlaybackSupported()`는 **false**, `HapticGenerator.isAvailable()`도 **false**였다. 음향 재생·녹음은 수행하지 않았고 임시 dex는 삭제했다. 이 기기에 오디오 결합 연속 촉각 전송을 사용할 근거가 없다. 엔벌로프도 위 실제 능력 탐지에서 미지원이었다. 숨김/시스템 전용 진동 세션 API를 일반 앱에서 사용하지 않는다.

조회한 진단 클래스의 핵심 코드는 아래와 같다. 앱에 새로운 오디오 출력 경로를 추가한 것이 아니다.

```java
System.out.println("audioHapticPlaybackSupported=" + AudioManager.isHapticPlaybackSupported());
System.out.println("hapticGeneratorAvailable=" + HapticGenerator.isAvailable());
```

## 후속 비교 E/F — 강도 차이 미체감 / 겹침도 거침

- E는 한 OS 호출 안에서 amplitude60→130→220을 각각600ms씩 보내며 총1800ms다. 실제 강도 제어의 체감을 파형 교체 끊김과 분리한다. 알려진 순서의 진단이므로 블라인드80% 시험 합격으로 사용하지 않는다.
- F는 C와 같이60ms마다10회 호출하되, 앞선9개 요청에만60ms 겹침 꼬리를 붙인다(각120ms 요청, 마지막은60ms). 계획상 마지막 요청의 끝은600ms다. 겹친 구간을 합산한 요청 길이는1140ms지만 서로 교체되는 효과이므로1140ms를 순서대로 재생하는 시험이 아니다. 앱 일정 오차와 OS 정리 시간은 별개다. 겹침이 체감 끊김을 줄이는지 확인하는 합성 비교이며 live 출력에 적용하지 않았다.
- 중지·실패·화면 이탈 취소와 최대40ms 일정 지연 중단은 동일하다. 원본 마이크 입력은 사용하지 않는다.
- 사용자는 E에서 **진동 자체는 느꼈지만 강도 차이는 없었다**고 재확인했다. F와 C는 **둘 다 거칠다**고 보고했다. 겹침을 추가하는 것만으로 반복 교체의 체감 문제가 해결되지 않았다. 이 방식을 live에 적용하거나 합격으로 처리하지 않는다.

[완료 명령 기록](evidence/issue18-ef-command-summary.txt)에서 E는 각1회, F는 각10회 호출로 완료했다. F의 관찰된 앱 일정 최대 지연은7–23ms였다. E의 [시스템 파형 기록](evidence/issue18-ef-os-waveforms.txt)은0.24→0.51→0.86 amplitude, scale NONE1.00/adaptiveScale1.00을 보여준다. 이는 서로 다른 명령이 OS에 도달했다는 증거이며 실제 모터 강도가 달랐다는 증거가 아니다. `hasAmplitudeControl=true`만으로 촉각 강약 전달이 검증되지 않았음이 드러났다.

추가로 기존의 분리된 약/중/강100ms 버튼을 비교했고, 사용자 보고는 **세 버튼 모두 비슷함**이었다. 이 기존 진단은 attributes를 지정하지 않아 초기 시스템 기록의 usage가 UNKNOWN이며 E/F의 TOUCH와 다르다. 따라서 결과를 동일 조건의 대체 실험으로 해석하지 않는다.100ms 초기 과도 반응이나60–220 구간의 체감 압축 등도 아직 분리되지 않았다. 물리 센서 없이 기기 전체가 강도 제어를 지원하지 않는다고 단정하지 않는다.

E 테스트는 누락 패턴으로 RED(5s) 후 구현됐고 전체167tests/build/lint가43s에 통과했다. F의 유한 겹침 테스트도 RED(3s) 후 구현했으며, 최종 **168tests/0failures/0errors + assembleDebug/lintDebug, BUILD SUCCESSFUL36s**를 확인했다. 최종 APK SHA-256은 `7d9d9066398e1b44f39a5e9ee99c7e4612909779044a22cf4e7425f300c375a6`이다. 초기166개 통과 기록과 구분한다.

### 전체 강도 범위 G/H — 같은 길이에서 강도 차이 미체감

G는 요청 amplitude1, H는255이며 둘 다 같은 TOUCH 어댑터로600ms를 한 번만 요청한다. 숫자는 물리 강도 비율이 아니다. 마이크·DSP·live scheduler와 시스템 강도 설정은 바꾸지 않는다. 동일한 착용 상태에서 충분히 쉬고 각각 실행해 차이를 확인하며, 하나가 안 느껴지거나 둘이 비슷한 결과도 그대로 기록한다. 순서/라벨이 보이는 탐색 실험이므로 블라인드 합격이나 강도3단계 정확도 근거로 사용하지 않는다.

추가 테스트는 누락 enum으로 RED(39s)를 확인했다. 비교 테스트7개와 assembleDebug/lintDebug가40s에 통과했고, 이어 전체 **169tests/0failures/0errors/0skipped**가39s에 통과했다. APK는56,232,469bytes, SHA-256 `d966e0c11ba0c03f447b76032ebff7d05cb3855a7abe943780157ad31df649a0`이다. 읽기 전용 검토에서 Critical/Important 결함은 없었다.600ms 직전 상태와 정상 완료 때 cancel 부재를 직접 검사하는 테스트는 경미한 추가 보완 여지다. 소스0ce3638의 이 APK를 install-r로 설치하고 실제 G/H 화면을 확인했다. 사용자는 **G/H 모두 진동하지만 비슷함**으로 보고했다.

### 설치된 삼성 베타 펌웨어의 표준 파형 처리 조사

기기는 One UI9(`ro.build.version.oneui=90000`)/Android17/API37, 빌드 `L300XXU2ZZI1`이며 사용자가 베타 참여 중임을 확인했다. 사용자는 삼성 기본 설정의 약함/강함 미리보기에서는 차이가 느껴진다고 보고했다. 미리보기의 패턴/길이를 통제한 시험은 아니므로, 이것만으로 동일 길이의 연속 진동 강약이 검증됐다고 판단하지 않는다.

G/H 두 쌍을 시각으로 대응시킨 결과 앱 요청은1/255였지만 삼성 HAL은 네 번 모두 `intensity=10000` 쓰기를 기록했다. 처음에는 이 값이 시작 기본값인지 실제 강도 고정 원인인지 구별되지 않았다. 이어 **같은 워치에서 읽은 services.jar의 DEX**를 분석해 표준 `SetAmplitudeVibratorStep.play()`가 amplitude를0/비0으로 구분하고, 비0인 경우 길이에 따라 모터를 켜지만 `changeAmplitude`/`setAmplitude`를 호출하지 않는 것을 확인했다. 클래스 전체에도 두 호출이 없다. 별도의 `AbstractVibratorStep.changeAmplitude`와 `VibratorController.setAmplitude` 구현은 남아 있다.

[AOSP 기준 구현](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/vibrator/SetAmplitudeVibratorStep.java)은 비0 구간에서 `changeAmplitude(amplitude)`를 호출한다. 비교한 AOSP main은 삼성 펌웨어와 동일 revision이라는 뜻이 아니다. 설치된 펌웨어의 파형 경로에서 강도 크기가 전달되지 않는 코드와 G/H 결과가 일치한다는 것이 현재 근거다. 삼성 설정 쪽은 별도 magnitude와 설정 표(`0/3500/6700/10000`)를 사용하는 경로가 있다. 모터 자체의 물리 한계나 모든 Watch7/펌웨어 버전으로 일반화하지 않는다.

[분석·재현 기록](evidence/issue18-firmware-path.txt)에 파일 해시, 호출 조사 범위와 전후 비교 절차를 남겼다. 시스템 JAR/DEX·전체 역어셈블 결과는 저장소나 APK에 재배포하지 않는다. 차단 목록의 삼성 magnitude setter나 시스템 전용 vendor 권한을 우회하지 않는다. 공개 삼성 확장 factory는 고정 패턴용이며 임의 PCM 강약을 연속 표현하는 해결책으로 검증되지 않았다.

당시 해결 후보는 새 베타/정식 펌웨어에서 **동일한 APK·동일600ms G/H**를 재검증하는 것이다. 사용자가 새 업데이트를 확인하고 직접 진행하겠다고 했다. 알려준 표기는 `l300xxu2k1/l300OXM2zzk1`이며 전체 AP 빌드명은 업데이트 후 기기에서 확인한다. 업데이트가 이 결함을 수정했다는 공식 근거나 실기기 결과는 아직 없다. 업데이트 전후 결과가 확보될 때까지 live 강도 전달과 끊김 수정, #18/#37/#39 합격을 보류한다.

**업데이트 후 결과:** 실제 AP는 `L300XXU2ZZK1`, One UI9/Android17/API37로 확인했다. 설치된 APK 해시는 위 `d966e0…`와 같고 화면 유지 설정0/원래 강도 설정10000도 유지됐다. 사용자는 G/H가 **업데이트 전처럼 둘 다 비슷함**이라고 보고했다. 새 services.jar의 표준 파형 클래스는 `.source` 추적 표식을 제외하면 이전과 완전히 같으며, 여전히 강도 변경 호출이 없다. 따라서 이 업데이트는 해당 경로의 문제를 해결하지 않았다. [업데이트 전후 기록](evidence/issue18-zzk1-regression.txt)을 남기고 강도 숫자만 바꾸는 반복 실험을 중단한다. 일반 앱에서 실제 강약을 전달할 해결 경로가 검증될 때까지 관련 기능과 최종 합격을 미완료로 유지한다.

## 물리 지연 측정 절차 — 아직 미실시

1. 원본 음성 대신 공개 권리/자체 생성한 합성 톤·노크·진폭 변화만 사용한다. 스피커 재생 명령 시점은 공기 중 소리 발생 시점과 구별한다.
2. 워치 마이크 옆의 독립 음향 임계 검출기에서 실제 소리 도달의 디지털 펄스 `t_sound`를 얻는다. 손목/워치에 부착한 독립 접촉 센서로 물리 모터 반응의 펄스 `t_motor`를 얻는다. 두 펄스를 같은 계측기 시계로 수집한다. 원본 마이크/접촉 오디오를 저장하지 않고 이벤트 시각만 보관한다.
3. 배경 잡음·무음·모터 꺼짐으로 임계값과 센서 교차 간섭을 먼저 확인한다. 진동 자체의 소리를 `t_sound`로 오인하지 않도록 스피커 사건 식별과 센서 배치를 검증한다. 약한 입력에서도 검출기가 사건을 놓치지 않는지 확인한다.
4. 앱 오디오 프레임 첫 샘플 시각, DSP/매핑 완료, OS 진동 호출은 별도 단조 시계 기록으로 구분한다. 외부 계측기와 시계 동기화 근거 없이 앱 시각을 외부 시각에서 빼지 않는다. 이 문서의 비교 드라이버는 앱 내부 전체 지연 수집기를 구현하지 않았다.
5. 재현 가능한 입력 종류·강도별로 반복한다(권장 총60회 이상, 각 조건20회 이상). `trial, case, t_sound_ns, t_motor_ns, response/status`만 기록한다. 미반응은 누락하지 않고 실패로 집계한다.
6. 각 유효 사건의 `t_motor - t_sound`를 정렬하고 nearest-rank `ceil(0.95*N)`의 P95를 보고한다. 전체/조건별 N·미반응 수·P50/P95/최대와 센서 오차를 함께 기록한다. 목표는 물리 P95≤500ms이며 미측정·미반응을 제거한 선택적 표본으로 합격 처리하지 않는다.

외부 계측이 없으면 앱 명령 지연까지만 보고하고 물리 지연은 미측정으로 유지한다. 카메라 영상을 증거로 쓸 경우 원본 음성 녹음을 포함하지 않고, 광학 기준 신호/실제 모터 접촉 센서 표시 및 프레임 해상도·오차를 명시한다.

## 실제 감지 경로의 수치 비교 보완 (2026-11-13)

사용자는 ZZK1 업데이트 후에도 작은/큰 소리 모두 비슷한 길이·세기의 짧은 진동이 끊겨 반복된다고 보고했다. 소리 유무만 알리는 동작은 프로젝트 목표의 합격이 아니다. 10초 간격 화면 표본은 짧은 입력 사건을 놓치므로 실제 DSP 프레임 경계와 진동 요청 경계를 집계해 원인을 구분한다.

디버그 앱만 세션마다 `HapticTelemetry`와 투명한 `TracingEnvelopeDevice`를 생성한다. DSP 처리·매핑·스케줄러의 출력 정책은 바꾸지 않는다. 25개 프레임(정상 입력 시 500ms)마다 다음의 수치만 모으며, 소비자가 늦으면 최신 집계 한 개로 교체한다. 원본 PCM·음성·AI 소리 이름·기기 연결 식별자는 모으지 않는다.

- 입력 RMS/엔벌로프/소음 추정/게이트 뒤 level/요청 강도의 최소·최대, 0이 아닌 요청 프레임 수와 스케줄러 거부 수.
- DSP 소비 콜백 진입 간격과 그 시점의 프레임 나이. DSP 계산/동기식 OS 호출 전에 시각을 읽는다. 오디오 첫 샘플 시각은 기존 캡처의 추정치이며 물리 소리 발생 시각이 아니다.
- 실제 Waveform API 호출 시도 수·간격, 요청한 전체 파형 길이 및 명시적인 양의 amplitude 범위. `defaultAmplitudeSegments`는 값 -1의 요청 수다. 양의 amplitude가 없으면 최소/최대 0으로 기록하므로 이 수치를 모터 무출력으로 해석하지 않는다.
- cancel 호출 시도 수. API 시도는 성공·물리 모터 반응과 다르며 예외는 기존 렌더러로 그대로 전달한다.

`UllimTrace` 로그 쓰기는 기존 메인 heartbeat에서 최신 집계를 가져와 실행하며 마이크/DSP 콜백에서 로그 I/O를 하지 않는다. 로그는 개별 프레임/개별 API 호출 전체의 원본 이벤트 목록이 아니다. 마지막 25개 미만 프레임은 포함되지 않을 수 있고 메인 스레드가 늦으면 중간 집계가 교체된다. 엔벌로프 요청은 래퍼가 원래 요청 그대로 전달하지만 이 Waveform 전용 호출 수에는 포함하지 않는다. 대상 워치는 엔벌로프 미지원이다.

실기기 시험은 앱 설치 후 짧은 정숙/작은 소리/큰 소리 구간을 비교하고 일반 중지 버튼으로 끝낸다. 실제 입력 RMS와 요청 intensity/amplitude가 달라지는지, 지속 입력 구간에도 호출 교체가 반복되는지 확인한다. 위 수치로 실제 모터 가속도·물리 P95·블라인드 정답률을 대신하지 않는다. 이 코드는 원인 조사 도구이며 끊김/강약 수정의 성공을 뜻하지 않는다.
